# Deployment runbook: game-catalog

Generated by genproj (docker-container capability, registry=ghcr.io,
network mode=bridge, watchtower=true, homepage=true), then hand-corrected:
the CI described below is **Buildkite**, not CircleCI (house rule: Buildkite
is the sole CI vendor).

## 1. Build & publish the image

`.buildkite/pipeline.yml` has a `docker_publish` step that builds a
`linux/amd64` image and pushes it to `ghcr.io/nickbrett1/game-catalog` on every
push to `main` (tagged with the commit SHA and `latest`).

- The registry namespace (`nickbrett1`) is derived from the authenticated
  GitHub identity at generation time.
- Registry credentials come from **Doppler** at job runtime — the pipeline
  reads `GHCR_UPDATE_TOKEN` from project `common`, config `prd` using the
  agent's `DOPPLER_TOKEN`. There is no CI "context" object and no credential in
  the agent environment hook.

### Renaming the repo — the one thing that breaks silently

`IMAGE` and `CACHE_REF` in `.buildkite/pipeline.yml` are literal strings. If
the GitHub repo is renamed without updating them, CI keeps publishing to the
**old** GHCR path, the old package still exists and still pulls, and the host
carries on running stale code with a green pipeline. Update the repo rename and
these two lines in the same push, then confirm the new package appears.

## 2. Deploy on ryzen

The deployment is **not** on a Synology NAS any more. All four containers run on
ryzen from `/srv/docker/game-catalog/`:

| container | port | image |
|---|---|---|
| `game-catalog` | 3003 | `ghcr.io/nickbrett1/game-catalog` (Dagster dev) |
| `game-catalog-manual` | 3004 | same image, `uvicorn mailroom.manual_api:app` |
| `dagster-mcp` | 8770 | `ghcr.io/nickbrett1/dagster-mcp` |
| `catalog-mcp` | 8766 | `ghcr.io/nickbrett1/catalog-mcp` |

1. `cd /srv/docker/game-catalog`
2. `docker compose down` — **before** any `up -d`. A plain `up -d` after a
   service rename leaves the old containers running as orphans, which means two
   Dagster daemons on one `DAGSTER_HOME`.
3. `docker compose up -d`

For non-Synology hosts this is the same as `docker compose up -d`.

## 3. Auto-updates with Watchtower (poll model)

`watchtower-nick` on ryzen polls the `nickbrett1` namespace every 60s and
recreates a container when the image digest changes — no inbound ports from CI
are required.

- This project opts in via the `com.centurylinklabs.watchtower.enable=true` label.
- After a registry path change, confirm watchtower picks up the **new** path
  rather than continuing to track the old tag.
- **Public packages**: no credentials needed on the host.
- **Private packages**: `docker login ghcr.io` on the host once (Watchtower uses
  the Docker daemon's credentials).

## 4. Rolling back a bad update

Watchtower recreates the container on every push to `main`, so a broken build
can reach the host. Every image is also tagged with its commit SHA, so you can
pin the compose file to a known-good build while you fix the repo:

1. Find the SHA of the last good commit (GHCR package page, or `git log`).
2. In `docker-compose.yml`, change the image to the pinned SHA:
   `image: ghcr.io/nickbrett1/game-catalog:<commit-sha>`
3. `docker compose up -d`

Watchtower watches the tag referenced by the compose file, so a pinned SHA tag
will not be overwritten until you move the image back to `latest`.

## 5. Homepage dashboard

Homepage runs on ryzen at `/srv/docker/homepage/` (`network_mode: host`).

The compose file carries `homepage.*` labels, which the homepage Docker provider
discovers automatically — prefer those over appending `deploy/homepage-services.yaml`.

- Server-side widget URLs are `http://127.0.0.1:PORT` (homepage is on host
  network); browser-facing `href` is `http://ryzen:PORT`.
- `container:` refs resolve against the ryzen socket, so a renamed container
  breaks its status readout unless the ref is updated.
- An edit is not enough: use `docker compose up -d --force-recreate` in
  `/srv/docker/homepage`, and `curl http://localhost:3000/api/revalidate` if the
  page is a stale Next.js prerender.

## 6. Networking notes

- Compose project has **no default network** — only two external ones:
  `msgvault_default` (so `MSGVAULT_URL=http://msgvault:8080` resolves) and
  `ai_proxy`. Both are load-bearing; check with `getent hosts msgvault` inside
  the container after any compose change.
- DNS between containers resolves by `container_name:`, not by service name.
  `DAGSTER_URL` defaults to `http://mailroom:3003` and must follow whatever
  container name the Dagster container actually has.
- Network mode is `bridge`. If a container needs fixed UDP ports or multicast,
  set `networkMode: host` — bridge cannot pass multicast reliably.
- For private services (Tailscale-only), set `publishPort` to
  `127.0.0.1:<port>:<port>` so the port is not exposed on the LAN.
- Homepage href/widget URLs use the **published host port** (the left-hand side
  of `publishPort`), never the container port.

## 7. Data mounts

The shared catalog volume is bind-mounted at `${DATA_DIR}:/data` by three
containers: `game-catalog`, `catalog-mcp`, and (from its own compose file)
`pshelf`. `dagster-mcp` mounts nothing.

- `DATA_DIR` is an absolute host path in `.env`. It is the **single most
  dangerous string in this repo**: if it points somewhere that does not exist,
  Docker silently creates an empty directory and pshelf renders
  "No catalog loaded" instead of failing loudly. This has already happened once.
- `catalog-mcp` mounts `:rw` because SQLite needs the `-shm` WAL index even for
  reads; read-only-ness is enforced in-code via `PRAGMA query_only=ON`.
- `data/` is owned by uid 1026 and the containers run as root, so no chown is
  needed. Keep it that way or you inherit an ownership bug.

## 8. Healthchecks, env vars and system packages

All three are config-driven on the `docker-container` capability — the
generated Dockerfile, compose file and Homepage widget stay consistent:

- `healthcheck`: `none` (default for Python), `http:<path>` (e.g.
  `http:/healthz`; installs `curl` on Python images), or `command:<cmd>`.
  The Homepage widget is only emitted when a real health endpoint exists.
- `envVars`: emitted into the compose `environment:` and `.env.example`.
  Compose entries use `${KEY:-default}` interpolation so a host-side `.env` can
  override them.
- `pythonDependencies`: runtime Python deps emitted into `[project]`
  dependencies of `pyproject.toml`.
- `aptPackages`: Debian packages installed in the runtime image via apt.
- `command` / `entrypoint`: override the container CMD/ENTRYPOINT (exec form).
  When the value points at `/usr/local/bin/<script>`, genproj copies
  `scripts/<script>` from your repo into the image (chmod +x) — keep the script
  in `scripts/`.

Regenerate with `overwrite: true` to apply these to an existing repo — existing
app code is preserved; only generated infra files are updated. Note that
regeneration will reintroduce the stale CircleCI prose and the `mailroom`
naming, so re-apply the corrections above afterwards.
